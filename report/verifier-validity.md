# HWE-bench v1.1：验证器有效性与评测边界

> 核心问题：**Agent 的补丁通过特定仿真测试，距离证明 RTL 功能、规范与系统集成正确性，还有哪些差别？** 本文区分官方明确记录、现有可复现实验与待验证推论，不把局部案例推导成全基准的误判率。

## 1. 证据与总体判断

HWE-bench 将真实仓库中的 Bug 修复转化为可执行的 Agent 任务，其 Fail-to-Pass 判据（错误基线 FAIL、参考修复 PASS）为自动回归提供了有效基础；但 **PASS 只能证明给定评分器在有限条件下接受了提交**，而非对所有输入、可实现变体、规范约束和系统集成的充分证明。判断是否可靠，需分别考虑 Bug 激活（Activation）、可观测性（Observability）与 Checker 判定条件。

证据等级约定：**官方记录**＝[v1.1 发布说明](https://pku-liang.github.io/hwe-bench/v1.1.html)明确披露；**本研究实测记录**＝公开脚本与结果可核查的局部执行；**静态诊断**＝代码或文档推理，尚未执行目标负例；**待验证假设**＝缺少完整代码或执行证据。不是每个静态发现都已产生实际错误评分。

## 2. 官方确认的修订及其含义

| 主题 | 官方事实 | 验证意义及边界 |
| --- | --- | --- |
| 测试覆盖与判别力 | v1.1 变更了 **188** 份隐藏测试；**33** 个任务加强行为检查，其中 **29** 个任务至少有一份此前通过的候选在新增检查下失败 | 已证实特定弱 Checker 会漏判；不能用 29/417 估计全部剩余漏检率 |
| 参考实现耦合 | **60** 个测试依赖内部信号、层次引用、源码文本或模拟宏等实现细节 | 合理替代实现可能遭到误拒；不能把所有编译失败当成 RTL 错误 |
| 测试文件归属 | **91** 个测试新增受保护文件列表，在评分前恢复相应测试文件 | 避免 Agent 修改影响隐藏 Checker；不代表发现了 91 起作弊 |
| 构建环境 | OpenTitan **#14681/#16176** 固定 setuptools_scm 6.4.2；Rocket Chip **#177/#387/#1493/#1761/#2167** 延长测试超时；另为 7 任务调整容器时限 | 环境/依赖超时与 Agent 修复能力应区分 |
| 题面与参考答案 | **50** 份题面、**1** 份参考修复修改；本次共 **208 个不同任务**发生变动 | 188/50/1 和 91/60/33 存在统计口径差异与交集，不能简单求和 |

官方对 v1.0 中至少一套系统失败的 **148 题**和六套系统全部通过的 **269 题**分别进行了复查；v1.1 保留原先的 Fail-to-Pass 基础判据。以上是[作者修订说明](https://pku-liang.github.io/hwe-bench/v1.1.html)中的事实，不是本研究自行复跑 417 题的结果。

### 2.1 正确行为被错误实现假设阻断：False Negative

**OpenTitan #12505**：v1.0 替代的 ASSERT 宏只接受两参，不能容纳合法修复里带时钟参数的断言；v1.1 更新宏桩。这一问题及修复由官方报告。本项目另外对**旧新宏签名**执行了局部 Icarus 编译对照（[脚本](../analysis/replay.py)、[输出](../evidence/replay.json)），**没有**重跑该题完整 VCS 协议测试。[PR](https://github.com/lowRISC/opentitan/pull/12505)

**OpenTitan #10732**：旧测试通过固定层次路径关闭内部断言；合法替代实现没有保留该断言时发生交叉模块引用错误。v1.1 改成仅在声明存在时关闭。此项来自[官方发布说明](https://pku-liang.github.io/hwe-bench/v1.1.html)，本项目没有独立重跑该任务。[PR](https://github.com/lowRISC/opentitan/pull/10732)

### 2.2 Agent 修改影响最终判定：Verifier Ownership

v1.0 的一些任务允许 Agent 编辑原有 Testbench/DV 文件；隐藏测试如果使用这份副本，就可能被被测修改影响。v1.1 对 91 题增加测试拥有文件的基线恢复机制，设计代码修改依然保留。本项目对 **OpenTitan #21632** 的恢复步骤进行了**局部文件指纹实验**（[脚本](../analysis/owned.py)、[结果](../evidence/owned.json)），证明的是文件恢复行为，不是发生过真实作弊或所有正确修复均被保留。

## 3. Ibex #54：已有实证与新的待核路径

### 3.1 本研究已发布的局部实测

[分析代码](../analysis/replay.py) 与 [结构化结果](../evidence/replay.json) 已记录对**错误基线、参考修复和七份公开历史候选补丁**运行 v1.0/v1.1 官方脚本，并在受限输入域中枚举 **65,536 种 16 位编码**，比较压缩标志、非法标志与展开指令。因此“七份候选及穷举结果尚未核查”不符合本仓库当前公开成果；这些结果已有来源和复现路径，但本轮文档核查**没有再次执行**它们。

七份历史候选在官方脚本中均为 PASS，而扩展输入检查发现：**四份候选各有 32 个输入与参考不同**，它们将一组合法 HINT 编码误判为非法；另有一份对保留编码 0x6101 的结果不同，需要结合规范单独解释；两份在限定观测域内无差异。这构成特定输入条件下的**真实判别力缺口证据**，不能外推为最新七套 Agent 或全体 417 题的表现。

### 3.2 只改 instr_o 的错误补丁是否也能 PASS？

另有一项**待做独立源码复核**的主张：#54 v1.1 的五项 HINT 测试检查 is_compressed_o 与 illegal_instr_o，而 instr_o 仅被打印、未参与 PASS/FAIL。当前材料提供了相关脚本的简化摘录；**本轮未重新取得完整的 v1.1 tb_script 核对每一项直接或间接判定条件**，因此不把这一条作为已经重新确认的独立事实。

更重要的是，它与上面的“32 个非法标志差异”不是同一类缺陷。要证明新路径，需构造**只影响展开后 instr_o、其余被测输出正确**且按 RISC-V 规范确实产生错误行为的候选，实测原脚本 PASS、新增独立 Oracle FAIL。不能仅凭未发现 instr_o 断言，就宣称已经发生这种误判。

建议证据链：固定 v1.1 #54 任务的完整 tb_script → 提取全部检查表达式和输入 → 构造具有语义副作用的独立错误变异 → 运行原脚本 → 使用审查过的参考译码/交叉实现/合法 HINT 规范判断 → 保存两个判据的差异。

## 4. 从仿真修复能力到完整芯片验证

**Ibex PR #2117** 是真实的寄存器堆故障注入安全修复；上游作者明确记载对 **Yosys 综合网表进行形式化 Fault Injection 验证**。[PR 原文](https://github.com/lowRISC/ibex/pull/2117)。本项目[研究底稿](research-notes.md)把它列为不在 417 个任务中的候选，应该用作**评测范围对照**，不能描述成 HWE-bench 收录任务，也不能直接断言它为何未入选。

RTL 仿真、SVA/形式化性质检查、CDC 静态分析、综合网表故障分析、STA 与系统级回归的保证目标并不相同。HWE-bench 的可执行修复测试具有工程价值，但不承担统一验证上述所有 sign-off 能力的职责。另有[公开 Issue #3](https://github.com/pku-liang/hwe-bench/issues/3)讨论 Ibex 单模块测试可能遗漏上层连接和集成变动；这是有具体案例的**评测范围质疑**，不是对全库集成漏检率的统计。

商业 EDA 依赖也是复现边界：OpenTitan 245 题需要自行提供合法可用的 Synopsys VCS 环境及镜像，其余任务也可能涉及不同构建/仿真工具；不能简单认为所有 172 题只需同一种仿真器。参见[官方运行说明](https://github.com/pku-liang/hwe-bench#docker-images)。

## 5. 推荐的错误类型与实验优先级

Benchmark 最好独立统计：构建/依赖失败、RTL 编译错误、Testbench 编译/展开错误、仿真未启动/超时、断言或 Scoreboard 功能失败，以及文件污染与结果无效。**环境 INVALID 不应直接与功能 FAIL 混为一谈**；编译失败需进一步判断源自被测设计还是受信验证器自身。

| 优先级 | 实验 | 目标证据 |
| --- | --- | --- |
| P0 | #54 的 instr_o 定向错误变异与原始脚本重放 | 原测试 PASS、独立规范 Oracle FAIL，确认新漏判路径 |
| P1 | 用增强输入及 Checker 重测 #54 的四份历史错误候选 | 拒绝这四份、接受参考与其他合法实现；证明增强判据有区分力 |
| P1 | #12505 同一候选在两版完整验证器中对照 | 隔离宏兼容性变化对任务结果的影响；现阶段仅有宏局部实验 |
| P2 | 选一项 Ibex 单模块 PASS 的候选上移至核级 Elaborate | 检查模块修复是否存在真实系统接线缺失；目前为研究计划 |

## 6. 结论

**Fail-to-Pass 是必要的自动化功能证据，但不是充分的整体 RTL 正确性证明。** HWE-bench v1.1 的官方修订已具体展示弱 Checker、参考补丁耦合、评分器文件污染和工具依赖的不同风险。本研究的 #54 局部实验进一步显示，历史候选通过官方测试的同时仍可能违反被遗漏的合法指令组合条件。后续需以独立 Oracle、正反变异、系统级检查与分阶段错误统计增强判别力，而不能凭个别案例估计全基准的真实误判比例。
